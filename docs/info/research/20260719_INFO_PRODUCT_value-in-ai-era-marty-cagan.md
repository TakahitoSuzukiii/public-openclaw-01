## 1. TL;DR（3行）

- 生成AIで「**つくる（デリバリー）**」コストが激減 → ボトルネックは上流の **戦略とディスカバリー（＝何をつくる価値があるか発見する工程）** に移った。
- 「エンジニアが遅い」は本当の問題ではなかった。真の問題は昔から **「競合より優れた解を思いつけていないこと」**。AIでそれが露わになった。
- **プロトタイプは誰でも作れる。でもプロダクトは別物**。AIに委ねてよいのは作業であって、**自分の判断力・思考を自動化してはいけない**（それが雇われている理由）。

---

## 2. 記事の要点

### ① ボトルネックは「ディスカバリー」へ
- プロダクト開発の3課題＝**戦略／ディスカバリー／デリバリー**。生成AIは全部を助けるが、**圧倒的に効くのはデリバリー**。
- 結果、ボトルネックは上流へ。戦略はCPO級が担うので、**現場PdMの真のボトルネック＝ディスカバリー**（顧客が競合を差し置いて選ぶ優れた解を見つける工程）。

### ② AIプロダクトでは「4つのリスク」が重くなる
- 『INSPIRED』の4リスク＝**価値(Value)／使いやすさ(Usability)／実現可能性(Feasibility)／事業成立性(Viability)**。
- AIが中核の「確率的プロダクト」（翻訳・自動運転等）では、ほぼ全リスクが一段重い（コスト構造が厳しく赤字が多い／安全性の要求が極端に高い／確率的挙動とのUI設計が難しい）。
- **最も過小評価されているのは「価値(Value)」リスク**。「クールだから」で作っても顧客は買わない。**現在のAIプロダクトの多くは中身が伴わないマーケティング**、と手厳しい。

### ③ 3つの組織モデルで未来が分かれる
| モデル | 実態 | AI時代の行方 |
|---|---|---|
| ① アジャイルPO | ディスカバリーが無い＝実はPdMでない | AIが代替可。**早くリスキリングを** |
| ② プロジェクト/フィーチャーチーム | 実態はプロジェクトマネジメント。意思決定は経営/ステークホルダー | ロードマップ項目の**約80%が期待成果を出さない**統計的欠陥 |
| ③ プロダクトモデル（Empowered） | 「機能リスト」でなく**「解くべき課題と成果」**を与えられる | シリコンバレーで急伸。**PdM＝ビルダー**、価値と事業成立性に責任 |

### ④ プロトタイプ ≠ プロダクト
- **Build to learn（学ぶために作る＝ディスカバリー）** と **Build to earn（稼ぐために作る＝デリバリー）** は別物。
- 誰でもプロトタイプを作れる時代でも、**PdM・デザイナー・エンジニアの異なる専門性**は依然必要。
- 名言: **「Claude Code でコードを“書ける”ことと、拡張性・耐障害性・信頼性・安全性の高いプロダクトを作るために Claude Code を“使いこなせる”ことは、まったく別のスキル」**。

### ⑤ AIは「判断の代替」でなく「判断力を育てる」ために
- プロジェクト的タスクは自動化してよい。だが **自分の判断力・思考は絶対に自動化するな**（＝雇われている理由）。
- 最良のAI活用＝**「パーソナル・プロダクトコーチ」**として、**プロダクトセンス（顧客・データ・ビジネスへの深い理解）** を養う手助けに使う。

## 3. 所感・エンジニア/キャリアへの示唆

- **「作れること」はもう差別化にならない**。差がつくのは「**何を作る価値があるか**を見極める力（ディスカバリー／価値の検証）」。エンジニアも“実装力＋課題発見・価値検証”の掛け算が効く。
- **80%失敗の教訓**: 言われた機能をこなす働き方（フィーチャーチーム）はリスク。**「課題と成果」で考える**癖をつけると、AI時代に強い。
- **判断を手放さない**: AIに下書き・調査・プロトタイプは任せ、**意思決定と思考は自分で持つ**。これは本ドキュメント群の運用原則（HITL・自分で検証）とも一致する。
- **転職・面接への転用**: 「Go×AWS×生成AIで作れます」だけでなく、**「なぜそれを作るのか（価値・課題）」を語れる**と刺さる。プロトタイプを見せる面接が主流化しているのも追い風。
