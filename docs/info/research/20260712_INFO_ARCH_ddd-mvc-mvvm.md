# 古典DDD / MVC / MVVM / DDD（エリック・エバンス）— 実践ガイド

> 作成日: 2026-07-12 / STATUS: INFO / TOPIC: ARCH
> 対象: Web アプリ／バックエンド開発における **古典DDD・MVC・MVVM・DDD（エリック・エバンスのドメイン駆動設計）**
> 図は全てプレーンテキスト（Mermaid 非依存）。

---

## 0. 全体像 — 「提示層の分離」と「ドメインの設計」は別レイヤーの話

本書で扱う4つは、実は**2つの異なる関心事**に分かれる。混同しやすいので最初に整理する。

```text
関心事A: 提示層（UI）の構造をどう分けるか
   MVC ──(データバインディング前提へ進化)──▶ MVVM

関心事B: 業務ロジック（ドメイン）をどう設計するか
   古典DDD（古典的ドメインモデル）──(戦略的設計を加えて全体化)──▶ DDD（エリック・エバンス）

両者は排他ではなく重なる:
   [ UI: MVC / MVVM ] ── [ アプリケーション ] ── [ ドメイン: DDD ] ── [ インフラ ]
```

- **MVC / MVVM** = 主に **UI（提示層）** をどう分割するかのパターン。
- **古典DDD / DDD** = 主に **ドメイン（業務ロジック）** をどう設計するかの思想。
- 実システムでは「UI は MVVM、ドメインは DDD」のように**組み合わせて**使う。

---

## 1. MVC（Model-View-Controller）

- **起源**: Trygve Reenskaug、1979年 Smalltalk。GUI の関心を3つに分離。
- **構成**:
  - **Model**: データと業務ロジック（アプリの本体）。
  - **View**: 画面表示（Modelを見せる）。
  - **Controller**: 入力を受けてModelを更新し、Viewを選ぶ。

```text
【MVC（古典GUI）】
 ユーザー操作 ─▶ [Controller] ─更新─▶ [Model] ─変更通知─▶ [View] ─表示─▶ ユーザー
                     │                                        ▲
                     └──────────── View を選択 ───────────────┘
```

- **Web MVC**（Rails, Spring MVC, Laravel 等）: リクエストを Controller が受け、Model を操作し、View（テンプレート）を返す。古典GUIのMVCとは通知の流れが異なる（サーバ往復型）。
- **狙い**: 関心の分離（表示・入力・ロジック）。**注意**: Model を「単なるDBのテーブル」に矮小化すると、業務ロジックが Controller に漏れて**ファットコントローラ**になりがち（→ ドメイン設計＝DDDの出番）。

---

## 2. MVVM（Model-View-ViewModel）

- **起源**: Microsoft の John Gossman、2005年（WPF/Silverlight）。**データバインディング**を前提にMVCを進化させたもの。
- **構成**:
  - **Model**: データ・業務ロジック（MVCのModelと同様）。
  - **View**: 画面（宣言的UI）。ViewModel と**双方向データバインディング**で結ばれる。
  - **ViewModel**: View の状態・振る舞いを**Viewに依存しない形**で保持する「Viewの抽象」。表示用の整形・入力コマンドを持つ。

```text
【MVVM】
 [View] ⇄(データバインディング: 双方向)⇄ [ViewModel] ─▶ [Model]
   宣言的UI      状態を自動同期            表示状態/コマンド    データ・業務ロジック
 ・View はコードをほぼ持たず、ViewModel を「バインドして映す」だけ
```

- **利点**: View にロジックを書かずに済み、**ViewModel をUIなしで単体テスト**できる。状態同期をバインディングに任せられる。
- **使われる場所**: WPF/Xamarin、そして考え方は Vue/Angular/Knockout など**SPA/リッチクライアント**の状態管理に通じる（React は厳密にはMVVMではないが「状態→UI」の宣言的思想を共有）。

### MVC / MVP / MVVM の違い（提示層パターンの比較）
| 観点 | MVC | MVP | MVVM |
|---|---|---|---|
| 仲介役 | Controller | Presenter | ViewModel |
| View との結合 | Controllerが介在 | PresenterがViewを直接更新 | **データバインディングで自動同期** |
| Viewのテスト容易性 | 中 | 高（Viewは受動的） | 高（ViewModelを単体テスト） |
| 代表 | Rails/Spring MVC | 旧Android等 | WPF/SPA |

## 3. 古典DDD（古典的ドメインモデル）

「古典DDD」は文脈により指すものが揺れるが、本書では **「エリック・エバンス以前／初期からある"古典的なドメインモデル"中心の設計」**、および **DDD の戦術的パターンだけを層状アーキテクチャに載せた古典的実践**を指すものとして整理する。

- **古典的ドメインモデル（Fowler『PoEAA』の Domain Model パターン）**: 業務ロジックを、DBの手続き（トランザクションスクリプト）ではなく**オブジェクトのネットワーク（ドメインオブジェクト）**として表現する。
- **古典的な層構造（レイヤードアーキテクチャ）**: エバンスの原典が示す4層 —
```text
【古典DDDの層（レイヤードアーキテクチャ）】
 [ UI / プレゼンテーション層 ]      ← MVC/MVVM はここ
 [ アプリケーション層 ]            ← ユースケースの調整（薄く保つ）
 [ ドメイン層 ]                    ← 業務ルールの本体（主役）
 [ インフラストラクチャ層 ]         ← DB・外部連携・技術詳細
   ※ 依存は上から下（この点をヘキサゴナル/クリーンで"内向き"に是正するのが現代DDD）
```
- **戦術的パターン**（後述の戦術設計と同じ道具）: エンティティ／値オブジェクト／集約／リポジトリ／ファクトリ／ドメインサービス。
- **「軽量DDD」の罠**: 戦術パターン（Repositoryやエンティティ等）"だけ"を導入し、**ユビキタス言語や境界づけられたコンテキストといった戦略的設計を欠く**と、DDDの本質的な効果が出ない。これを批判的に「軽量DDD（DDD-lite）」と呼ぶ。古典的実践がこの状態に陥りやすい。

## 4. DDD（エリック・エバンスのドメイン駆動設計）

**Eric Evans 2003年『Domain-Driven Design』**。DDDの本質は**戦術パターンの寄せ集めではなく、「戦略的設計＋モデル駆動設計」を含む全体像**。

### 4.1 3本柱
```text
【DDD の全体像】
① ユビキタス言語
    ドメイン専門家と開発者が"同じ言葉"を使い、その言葉をコードにも反映する
② 戦略的設計（大きく分ける）
    - 境界づけられたコンテキスト(Bounded Context): モデルが有効な範囲を区切る
    - コンテキストマップ: 複数コンテキストの関係（共有/顧客-供給/腐敗防止層 ACL 等）
    - コアドメイン/サブドメイン: どこに投資するかを見極める
③ 戦術的設計（コンテキスト内を作り込む）
    - エンティティ / 値オブジェクト / 集約(Aggregate)とルート
    - リポジトリ / ファクトリ / ドメインサービス / ドメインイベント
```

- **モデル駆動設計**: 分析モデルと実装を乖離させず、**同じモデル**を言葉・図・コードで一貫させる。
- **現代的な接続**: ドメイン層を UI/DB から独立させるため、**ヘキサゴナル／オニオン／クリーン**と組み合わせるのが定石（→ 別ドキュメント参照）。CQRS／イベントソーシングと組む発展形もある。

### 4.2 古典DDD との違い（要点）
| 観点 | 古典DDD（≒軽量DDDに陥りがち） | DDD（エバンス本来） |
|---|---|---|
| 主眼 | 戦術パターン＋層構造 | **戦略的設計＋ユビキタス言語**を含む全体 |
| 言語 | 実装用語中心 | ドメイン専門家と共有する**ユビキタス言語** |
| 分割 | 単一の大きなモデル | **境界づけられたコンテキスト**で分割 |
| 依存 | 上→下（DB寄り） | ドメイン中心（ヘキサゴナル等で内向きに） |
| 効果 | 限定的（形だけ） | 複雑ドメインの継続的な整理・拡張に効く |

## 5. 4つの関係を1枚で

```text
 提示層(UI)            アプリ層            ドメイン層              インフラ層
 ┌───────────┐      ┌───────────┐    ┌───────────────────┐   ┌───────────┐
 │ MVC / MVVM│──▶  │ ユースケース │─▶ │ DDD（戦略+戦術）    │─▶ │ DB/外部API│
 │(表示の分離)│      │(調整・薄い) │    │ 古典DDD→現代DDDへ発展│   │(詳細)      │
 └───────────┘      └───────────┘    └───────────────────┘   └───────────┘
 ・MVC/MVVM は「UIの分け方」、DDD は「ドメインの作り方」— レイヤーが違い、共存する
 ・古典DDD（層＋戦術）に、戦略的設計とヘキサゴナル等を足したのが現代のDDD実践
```

## 6. 学習用の実例 — Cargo Tracker

- **Cargo Tracker** は、エバンス『DDD』本の題材（貨物輸送ドメイン）を実装した**DDDの定番サンプル**。境界づけられたコンテキスト、集約、リポジトリ、ドメインイベント等を実コードで学べる。
- 参考プロジェクト（DDD＋要件定義/設計ドキュメントの事例）: k2works "Case Study Cargo Tracker" — RDRA 2.0 による要件定義、ドメインモデル分析、ADR などをセットで整備した学習用ケーススタディ。https://k2works.github.io/case-study-cargo-tracker/

---

## まとめ

> **MVC → MVVM** は「UI（提示層）の分け方」の進化（バインディング前提でViewを薄く・テスト可能に）。
> **古典DDD → DDD（エバンス）** は「ドメインの設計」の深化（戦術パターン＋層構造だけの"古典/軽量"から、ユビキタス言語・境界づけられたコンテキストを含む戦略的設計へ）。
> 両者はレイヤーが異なり**共存**する。複雑な業務を持つ Web/バックエンドでは、**UIは MVVM 等、ドメインは DDD、依存はヘキサゴナル/クリーンで内向き**、という組み合わせが王道。
