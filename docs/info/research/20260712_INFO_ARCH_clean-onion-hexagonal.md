# クリーン / オニオン / ヘキサゴナル / ポート＆アダプター — 実践ガイド

> 作成日: 2026-07-12 / STATUS: INFO / TOPIC: ARCH
> 対象: Web アプリ／バックエンド開発における **クリーンアーキテクチャ・オニオンアーキテクチャ・ヘキサゴナルアーキテクチャ（ポート＆アダプター）**
> 図は全てプレーンテキスト（Mermaid 非依存）。

---

## 0. まず結論 — 3つは「同じ思想」の兄弟

ヘキサゴナル・オニオン・クリーンは、名前も図も違うが、**同じ1つの原則**を別の語彙で表したもの:

> **依存の向きを常に「内側（ドメイン）」へ向ける。ビジネスロジック（ドメイン）を、UI・DB・フレームワーク・外部APIといった"詳細"から独立させる。**

- **ドメイン（業務ルール）が主役**。DB や Web は「差し替え可能な詳細」。
- 依存性逆転の原則（DIP）で、**内側がインターフェース（抽象）を定義し、外側がそれを実装**する。
- 効果: **テスト容易性**（DB や UI 無しにドメインを単体テスト）＋**技術的ロックイン回避**（DB/UI/FW を後から交換可能）。

```text
共通のルール（依存は内向き）
 [ フレームワーク/DB/UI/外部API ]   ← 外側（詳細・差し替え可能）
        │  依存は内向きだけ
        ▼
 [ アプリケーション（ユースケース） ]
        │
        ▼
 [ ドメイン（業務ルール・モデル） ]   ← 中心（何にも依存しない）
```

---

## 1. 共通の土台 — 依存性逆転（DIP）とポート＆アダプター

- **素朴な層構造の問題**: 「UI → ビジネス → DB」と上から下へ依存すると、ドメインがDB（詳細）に依存してしまい、DB交換やテストが困難。
- **依存性逆転**: ドメイン側に**インターフェース（ポート）**を定義し、DBアクセス実装（アダプター）はそのインターフェースを**実装する側＝外側**に置く。すると依存の矢印がドメインへ向き、ドメインは詳細を知らずに済む。

```text
【素朴な層（悪い）】ドメインがDBに依存      【DIP適用（良い）】DBがドメインの抽象に依存
 Domain ──▶ DBアクセス実装                Domain ──▶ [Repositoryインターフェース(ポート)]
   （交換・テスト困難）                                   ▲ 実装
                                          DBアダプター ──┘（外側が内側の抽象を実装）
```

この「**ポート（内側が定めた抽象インターフェース）＋アダプター（外側の技術実装）**」が3アーキテクチャ共通の仕掛け。

---

## 2. ヘキサゴナルアーキテクチャ（＝ポート＆アダプター）

**Alistair Cockburn が2005年に提唱**（別名 Ports and Adapters）。データストアやUIに依存せず、アプリを独立してテストできる疎結合アーキテクチャを目的とする（AWS 規範ガイダンス）。

### 2.1 構成
- **中心（六角形の内側）** = アプリケーション＋ドメインのコアロジック。
- **ポート（Port）** = コアに出入りする**技術非依存のインターフェース**。「外部アクターがコアと通信するための口」。USBポートに例えられる（規格を満たせば何でも挿せる）。
- **アダプター（Adapter）** = ポートに接続する**特定技術の実装**。技術情報を翻訳（REST・GraphQL・DB・メッセージブローカー等）。

### 2.2 2種類のポート／アダプター
- **駆動側（Driving / Primary、左）**: アプリを**呼び出す**側。例: REST/GraphQL/CLI/テスト → 入力ポート。
- **被駆動側（Driven / Secondary、右）**: アプリが**呼び出す**側。例: DB/外部API/メッセージ送信 → 出力ポート。

```text
【ヘキサゴナル】
   駆動側アダプター                         被駆動側アダプター
 (REST / GraphQL / CLI / test)          (DB / 外部API / MQ)
         │  入力ポート                          ▲  出力ポート
         ▼  (interface)                         │  (interface)
     ┌───────────────────────────────────────────────┐
     │      アプリケーション + ドメイン（コア）        │
     │      ・業務ルールのみ。技術を一切知らない        │
     └───────────────────────────────────────────────┘
 ※ 同じ入力ポートに REST と GraphQL の両アダプターを、コアに影響なく追加できる（USBの比喩）
```

### 2.3 AWS の観点（規範ガイダンス）
- **DDD と相性が良い**: 各アプリコンポーネントをDDDのサブドメインとして表現し、疎結合を実現。
- **Lambda に有効**: ビジネスロジックとインフラコード（DynamoDB アクセス等）を分離 → DB非依存で単体テスト可能、開発の俊敏性が上がる。
- **考慮点（デメリット）**: ①分離作業の**複雑さ**、②アダプター追加による**保守オーバーヘッド**（入出力が複数・将来交換が要る場合にのみ見合う）、③レイヤー増による**レイテンシ**。

## 3. オニオンアーキテクチャ

**Jeffrey Palermo が2008年に提唱**。**同心円（玉ねぎ）**で層を表し、**依存は常に内向き**。中心ほど安定・抽象、外側ほど変わりやすい・具体。

```text
【オニオン】外→内に依存
 ┌─────────────────────────────────────────┐
 │  UI / インフラ / テスト（最外殻・詳細）      │
 │  ┌───────────────────────────────────┐  │
 │  │  アプリケーションサービス            │  │
 │  │  ┌─────────────────────────────┐  │  │
 │  │  │  ドメインサービス            │  │  │
 │  │  │  ┌───────────────────────┐  │  │  │
 │  │  │  │  ドメインモデル(中心)   │  │  │  │
 │  │  │  └───────────────────────┘  │  │  │
 │  │  └─────────────────────────────┘  │  │
 │  └───────────────────────────────────┘  │
 └─────────────────────────────────────────┘
 ・リポジトリ等のインターフェースは内側で定義、実装は最外殻(インフラ)
```

- 特徴: DB を「一番外側の詳細」に追い出す点を強調（従来の「DB中心」設計へのアンチテーゼ）。

## 4. クリーンアーキテクチャ

**Robert C. Martin（Uncle Bob）が2012年に提唱**。ヘキサゴナル／オニオン／BCE／DCI 等を**統合・一般化**したもの、と本人が明言。**同心円4層**と**依存性のルール**が核。

### 4.1 4つの円
```text
【クリーンアーキテクチャ】依存は内向きのみ
 ┌───────────────────────────────────────────────┐
 │ Frameworks & Drivers（Web/DB/UI/デバイス）      │ ← 最外・詳細
 │  ┌─────────────────────────────────────────┐  │
 │  │ Interface Adapters                       │  │
 │  │ (Controller / Presenter / Gateway)       │  │
 │  │  ┌───────────────────────────────────┐  │  │
 │  │  │ Use Cases（アプリ固有の業務手順）    │  │  │
 │  │  │  ┌─────────────────────────────┐  │  │  │
 │  │  │  │ Entities（企業全体の業務ルール）│  │  │  │
 │  │  │  └─────────────────────────────┘  │  │  │
 │  │  └───────────────────────────────────┘  │  │
 │  └─────────────────────────────────────────┘  │
 └───────────────────────────────────────────────┘
```

### 4.2 依存性のルール（The Dependency Rule）
> **ソースコードの依存は、必ず外側から内側（＝上位方針）へのみ向く。内側の円は外側の円を一切知らない。**

- 内側を跨いで外へ制御を渡すには**依存性逆転**を使う（Use Case が出力ポート＝インターフェースを定義し、外側の Presenter/Gateway が実装）。
- Entities＝最も一般的・安定した業務ルール。Use Cases＝そのアプリ固有の手順。Interface Adapters＝内外のデータ形式変換。Frameworks＝Web/DB等の"詳細"。

---

## 5. ポート＆アダプターは「共通の実装メカニズム」

「ポート（内側の抽象インターフェース）＋アダプター（外側の技術実装）」は、名前としてはヘキサゴナル発祥だが、**オニオンの"インターフェースは内側・実装は外側"、クリーンの"依存性のルール＋出力ポート"と同じ仕組み**。3アーキテクチャに共通する実装手段。

```text
入力(駆動)アダプター → 入力ポート(IF) → [ユースケース/ドメイン] → 出力ポート(IF) → 出力(被駆動)アダプター
  REST Controller       UseCase IF          コアロジック          Repository IF        DB実装
```

---

## 6. 三者の対応関係（同じものを別語彙で）

| 概念 | ヘキサゴナル(2005/Cockburn) | オニオン(2008/Palermo) | クリーン(2012/Martin) |
|---|---|---|---|
| 中心（業務ルール） | アプリ＋ドメイン コア | ドメインモデル／ドメインサービス | Entities |
| アプリ固有の手順 | （コア内） | アプリケーションサービス | Use Cases |
| 内外の変換 | アダプター | UI/インフラ層 | Interface Adapters（Controller/Presenter/Gateway） |
| 技術詳細 | アダプター（REST/DB/MQ） | 最外殻（UI/インフラ/テスト） | Frameworks & Drivers |
| 抽象の置き場 | ポート（IF） | 内側で定義するインターフェース | 内側で定義（出力ポート等） |
| 依存の向き | 外→中心 | 外→内 | 外→内（依存性のルール） |

> 実務では厳密な区別より「**依存を内向きにし、ドメインを詳細から独立させ、境界をインターフェースで切る**」という共通目的を達成できているかが重要。

## 7. 実装イメージ（AWS 規範ガイダンスの Lambda ヘキサゴナル例）

Lambda にヘキサゴナルを適用し、ドメインをインフラ（DynamoDB）から分離した構成:

```text
lambda_handler
  └─ 入力ポート実装 (RecipientInputPort) ── ドメインモデル (Recipient: 業務ルールのみ)
        │  make_reservation() でドメインロジック実行
        └─ 出力ポート (IRecipientOutputPort) ◀── DynamoDBアダプター (DDBRecipientAdapter)
                                                    load()/save() で DynamoDB アクセス
```

- **ドメインモデル(Recipient)** は外部を一切知らず業務ルール（予約日重複チェック等）だけを持つ。
- **入力ポート**がドメインを呼び出し、**出力ポート（IF）**経由で永続化。実体は**DynamoDBアダプター**が実装。
- ファクトリで「入力ポート＋（出力ポート＋DBアダプター）」を組み立てて注入 → **DB非依存でユニットテスト可能**。

## 8. メリット / デメリット

**メリット**
- **テスト容易性**: ドメインをDB/UI無しで単体テスト（アダプターをモック差し替え）。
- **技術的ロックイン回避**: DB・UI・FW・外部APIを、ドメインへの影響ほぼゼロで交換可能。
- **複数の入出力に強い**: 同じドメインに REST も GraphQL も、RDB も S3 も、アダプター追加で対応。
- **DDD との親和性**: ドメイン中心設計を素直に実装できる。

**デメリット / 考慮点（AWS）**
- **複雑さ**: 分離・インターフェース設計のコスト。小規模CRUDには過剰になりがち。
- **保守オーバーヘッド**: アダプター層が増える。入出力が単一・交換予定なしなら割に合わない。
- **レイテンシ**: レイヤー追加で往復が増える可能性。

---

## 9. いつ使う / 避ける

- **使う**: 業務ルールが複雑／長寿命、複数クライアント・複数データストア、技術更新が頻繁、DDD採用、テスト重視。
- **避ける（過剰）**: 単純CRUD、短命なツール、入出力が1系統で将来も交換予定なし。→ 素朴な層構造で十分。

---

## まとめ

> ヘキサゴナル・オニオン・クリーンは**同じ思想の別表現**。共通原則は「**依存を内向きに固定し、ドメインを詳細（UI/DB/FW）から独立させ、境界をポート（インターフェース）で切ってアダプターで実装する**」。得られるのはテスト容易性と技術的自由度。代償は複雑さ・保守・レイテンシなので、**問題の複雑さに見合うときに導入**する。
