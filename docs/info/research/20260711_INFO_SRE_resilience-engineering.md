# システムのレジリエンス — 開発・運用保守・ポストモーテムの実践ガイド

> 作成日: 2026-07-11 / STATUS: INFO / TOPIC: SRE
> 対象: システム開発／運用・保守／ポストモーテムの文脈における「レジリエンス（resilience）」
> 方針: 概念の整理 → 開発時の設計パターン → 運用・保守の実践 → ポストモーテムによる学習、の順で体系化。図は全てプレーンテキスト（Mermaid 非依存）。

---

## 0. このドキュメントの狙い

分散システム・クラウド前提の現代では、**障害は「起きるか」ではなく「いつ起きるか」**。個々の部品を完璧にする（＝故障ゼロを目指す）よりも、**障害が起きても全体としてサービスを継続し、素早く回復し、経験から学んで強くなる能力＝レジリエンス**を設計・運用に組み込むことが重要になる。本書は開発・運用保守・ポストモーテムの3局面で、何をどう実践するかをまとめる。

```text
レジリエンスの4つの局面（本書の構成）
① 予見する(Anticipate) … 何が壊れうるか想定し、設計で備える  → 3章(開発)
② 監視する(Monitor)     … 兆候・異常を早く捉える              → 4章(運用)
③ 対応する(Respond)     … 起きた障害を封じ込め・復旧する      → 4章(運用)
④ 学ぶ(Learn)           … 障害から学び、再発を防ぐ            → 5章(ポストモーテム)
```

（この4能力は Erik Hollnagel のレジリエンス・エンジニアリングの枠組み ＝ respond / monitor / anticipate / learn に対応。）

## 1. レジリエンスとは — 定義と関連概念

### 1.1 定義
> **レジリエンス** = 予期する／しないに関わらず、変化・障害・過負荷といった外乱に対して、システムが**機能を（劣化しても）継続し、素早く回復し、経験から適応・改善していく能力**。

「壊れない強さ」ではなく「**しなやかに耐え、折れても立ち直り、次はもっと強くなる**」という動的な能力である点がポイント。

### 1.2 まぎらわしい近接概念との違い

| 用語 | 何を指すか | レジリエンスとの関係 |
|---|---|---|
| **信頼性 (Reliability)** | 一定期間、期待どおり動き続ける度合い（MTBF等） | レジリエンスが支える「結果」の一つ |
| **可用性 (Availability)** | 使いたいときに使える割合（稼働率 99.9% 等） | 同上。SLOで数値化する |
| **堅牢性 (Robustness)** | 想定内の外乱に対して**壊れずに耐える**力 | レジリエンスの一部。ただし想定外には弱い |
| **フォールトトレランス** | 部品が故障しても機能を維持する仕組み（冗長化等） | レジリエンスを実現する**手段**の一つ |
| **フェイルセーフ / フェイルソフト** | 故障時に安全側へ倒す／機能縮退して動き続ける | 対応(Respond)の設計方針 |
| **アンチフラジャイル (Antifragile)** | 外乱によって**むしろ強くなる**性質（N.タレブ） | レジリエンスの「学んで強くなる」側面の極端形 |

要点: **堅牢性は「想定内で壊れない」、レジリエンスは「想定外でも立ち直る」。** 両方必要だが、複雑系では後者の比重が増す。

### 1.3 Safety-I と Safety-II（考え方の転換）
- **Safety-I**: 「うまくいかないこと（故障・エラー）を減らす」= 失敗の除去に注目。
- **Safety-II**: 「**うまくいっていること**がなぜ成立しているかに注目」= 日常的に人・システムが行っている柔軟な調整（=レジリエンスの源泉）を理解し伸ばす。
- ポストモーテムでも「誰が失敗したか」ではなく「**普段どう成功を支えているか／その条件が今回なぜ崩れたか**」を見る（→5章のブレームレス文化）。

## 2. なぜ重要か — 障害は不可避

- **分散システムの現実**: ネットワーク分断・部分障害・遅延・タイムアウト・依存先の劣化は日常的に起こる。全構成要素を同時に健全に保つことは不可能。
- **複雑性による創発的障害**: 個々は正常でも、組み合わせ・タイミング・過負荷で予期せぬ障害が生まれる（カスケード障害・リトライストーム等）。
- **コスト構造**: 可用性を1桁上げる（99.9%→99.99%）ほど、故障ゼロ化のコストは指数的に増える。**「壊れない」より「壊れても素早く小さく収める」方が費用対効果が高い**局面が多い。

```text
故障ゼロを目指す発想（限界あり）        レジリエンス発想（現実的）
──────────────────────────         ──────────────────────────
部品を完璧に = コスト∞               障害は起きる前提
1点でも壊れると全体停止               影響を局所化(バルクヘッド)
                                    劣化運転で継続(グレースフル)
                                    素早く復旧(MTTR最小化)
                                    学んで再発防止(ポストモーテム)
```

## 3. 開発フェーズ — レジリエンス設計パターン

「予見(Anticipate)」を形にする層。外部依存・過負荷・部分障害を**前提に**設計する。

### 3.1 タイムアウト
- あらゆる外部呼び出し（DB・API・キャッシュ）に**必ず上限時間**を設ける。無限待ちは障害を伝播・滞留させる最大の元凶。
- **デッドライン伝播**: 上流のタイムアウト残時間を下流へ引き継ぎ、無駄な処理を打ち切る。

### 3.2 リトライ ＋ 指数バックオフ ＋ ジッター
- 一時的失敗は再試行で回復しうる。ただし素朴なリトライは**リトライストーム**を生む。
- **指数バックオフ**（1s→2s→4s…）で間隔を空け、**ジッター（ランダム化）**で同時再送の集中を防ぐ。
- **リトライ回数の上限**と、**べき等な操作にのみ再試行**を徹底。

```text
悪いリトライ（同期・即時・無限）        良いリトライ（指数+ジッター+上限）
失敗→即再送→失敗→即再送…              失敗→ (2s±random) →失敗→ (4s±random) → 最大N回で諦める
= 依存先へ集中砲火(リトライストーム)     = 依存先の回復を待ちつつ負荷分散
```

### 3.3 サーキットブレーカー（Circuit Breaker）
- 依存先が継続的に失敗しているとき、**回路を「開く」＝呼び出しを即座に遮断**し、素早くフォールバックを返す。依存先の回復余地を作り、自分のリソース枯渇も防ぐ。
- 状態遷移: **Closed（通常）→（失敗率が閾値超）→ Open（遮断）→（一定時間後）→ Half-Open（試験的に少量通す）→ 成功なら Closed / 失敗なら Open。**

```text
[Closed]  --失敗が閾値超-->  [Open]  --冷却時間経過-->  [Half-Open]
   ^                                                      |
   |------------------ 試験呼び出しが成功 -----------------|
                         （失敗なら Open へ戻る）
```

### 3.4 バルクヘッド（Bulkhead / 隔壁）
- 船の隔壁のように**リソースを区画分離**し、一部の障害・過負荷が全体に波及しないようにする。
- 例: 機能ごとにスレッドプール／コネクションプール／サービスを分ける。重い外部連携が全リクエストのスレッドを食い潰す事故を防ぐ。

### 3.5 フォールバック / グレースフルデグラデーション（縮退運転）
- 依存先が落ちても、**機能を全部止めるのではなく一部を落として動き続ける**。
- 例: レコメンドAPIが落ちたら「人気順」で代替、パーソナライズを諦めて基本機能は維持。

### 3.6 冗長化・多重化
- 単一障害点(SPOF)を排除。**Active-Active / Active-Standby**、マルチAZ・マルチリージョン、レプリケーション。
- ヘルスチェックと自動フェイルオーバー（ロードバランサ／オーケストレータ）。

### 3.7 べき等性（Idempotency）
- 同じ操作を複数回実行しても結果が変わらないよう設計（べき等キー等）。**リトライ・重複配信・二重送信に耐える**ための土台。

### 3.8 負荷制御（過負荷から自分を守る）
- **レート制限 / スロットリング**: 受け付ける流量に上限。
- **ロードシェディング**: 過負荷時に低優先度リクエストを意図的に捨て、コア機能を守る。
- **バックプレッシャー**: 処理能力を超える入力に対し上流へ「詰まっている」と伝え流入を抑える（キュー・非同期と組み合わせる）。

### 3.9 疎結合・非同期化
- 同期の直列依存はカスケード障害を招く。**メッセージキュー／イベント駆動**で疎結合にし、一時的な下流障害はキューで吸収（バッファリング）。

### 3.10 グレースフルシャットダウン
- デプロイ・スケールインの際、処理中リクエストを取りこぼさず、新規受付を止めてから安全に終了。

> 実務のコツ: これらは**組み合わせて効く**。「タイムアウト＋リトライ(指数+ジッター)＋サーキットブレーカー＋フォールバック」は外部依存呼び出しの黄金セット。

## 4. 運用・保守フェーズ — 監視(Monitor)と対応(Respond)

### 4.1 可観測性（Observability）
「監視(Monitoring：既知の指標を見る)」を超え、**未知の問題も内部状態から推測できる**ようにする。三本柱＋α:

| 柱 | 何を見るか | 例 |
|---|---|---|
| **メトリクス** | 数値の時系列（傾向・閾値） | レイテンシ、エラー率、飽和度、スループット |
| **ログ** | 個別イベントの記録 | 構造化ログ、監査ログ |
| **トレース** | 1リクエストの分散横断の経路・所要 | 分散トレーシング（どの依存が遅いか） |
| **(イベント)** | デプロイ・設定変更等の変化点 | 変更とインシデントの相関を取る |

- 監視の定番指標: **RED（Rate/Errors/Duration）**、**USE（Utilization/Saturation/Errors）**、Googleの**4 Golden Signals（レイテンシ/トラフィック/エラー/飽和度）**。

### 4.2 SLI / SLO / エラーバジェット
- **SLI（指標）**: ユーザ体験を測る実測値（例: 成功率、p99レイテンシ）。
- **SLO（目標）**: SLIの目標水準（例: 「99.9%のリクエストが 300ms 以内で成功」）。
- **エラーバジェット**: `100% − SLO`。**「許容される失敗の量」を予算として扱う**。
  - 予算が余っていれば**攻めた変更・リリース**をしてよい。
  - 予算を使い切ったら**新機能を止め信頼性向上に振る**（エラーバジェット・ポリシー）。
- 効用: 「絶対に落とすな」という不可能な要求を、**開発速度と信頼性のトレードオフを数値で回す**運用に変える。

```text
エラーバジェットの運用ループ
SLO=99.9% → 月間の失敗許容≒43分
├ 予算に余裕 → 積極的にリリース／実験（カオス含む）
└ 予算を消費し切った → リリース凍結・信頼性作業を優先
```

### 4.3 復旧速度の指標（MTTx）
| 指標 | 意味 | 下げ方 |
|---|---|---|
| **MTTD** (Detect) | 検知までの時間 | 監視・アラートの精度／網羅性 |
| **MTTA** (Acknowledge) | 一次対応着手まで | オンコール・エスカレーション整備 |
| **MTTR** (Repair/Recover) | 復旧までの時間 | Runbook・自動化・ロールバック容易性 |
| **MTBF** (Between Failures) | 平均故障間隔 | 設計品質・再発防止 |

> レジリエンスの主戦場は **MTTR（早く小さく復旧）**。「壊れない(MTBF↑)」だけでなく「早く直る(MTTR↓)」を重視する。

### 4.4 インシデント管理
```text
検知(Detect) → 対応(Respond) → 復旧(Recover) → 学習(Learn)
  監視/アラート   指揮系統(IC)     暫定回避→恒久      ポストモーテム(5章)
                  役割分担         ロールバック/切替
```
- **インシデントコマンダー(IC)** を立て、指揮・記録・対外連絡の役割を分離。
- **重大度(Severity)** を定義し、エスカレーション基準を明確化。
- 対応中は**タイムラインを都度記録**（後のポストモーテムの一次資料になる）。

### 4.5 オンコール・トイル削減
- 持続可能なオンコール（適切なローテーション、負荷平準化、燃え尽き防止）。
- **トイル**（手作業・繰り返し・自動化可能な運用作業）を計測し、自動化で削減。トイル過多はレジリエンスを蝕む。

### 4.6 Runbook / Playbook
- 典型障害への**手順書**を用意。着手の迷いを消し MTTR を短縮。「アラート → 対応手順」を紐づける。

### 4.7 カオスエンジニアリング（能動的に壊して学ぶ）
- 本番に近い環境で**意図的に障害を注入**（インスタンス停止・遅延・パケットロス・依存断）し、システムとチームの耐性を検証する。
- 原則（Principles of Chaos）: ①定常状態(正常の指標)を定義 → ②現実的な障害仮説を立てる → ③本番（or 近い環境）で実験 → ④影響範囲(blast radius)を最小化し自動停止を用意 → ⑤仮説とのズレから学ぶ。
- **ゲームデー**: 障害シナリオを予行演習し、Runbook・監視・人の連携を鍛える。

### 4.8 DR / BCP・バックアップ
- **RTO（目標復旧時間）／RPO（目標復旧時点）** を定義し、バックアップ・レプリケーション・フェイルオーバーを設計。**復旧はテストして初めて価値がある**（リストア訓練）。

### 4.9 キャパシティプランニング
- 需要予測・負荷試験・オートスケール。飽和(Saturation)を継続監視し、限界前に手当てする。

## 5. ポストモーテム — 障害から学ぶループ（Learn）

レジリエンスの最重要局面。障害を「二度と同じ形で起こさない」ための組織的学習。

### 5.1 ブレームレス（非難なし）文化 — なぜ人を責めないか
- 人を責めると、**情報が隠される**。隠蔽されれば根本原因に届かず、再発する。
- 前提: **「その時点の情報・制約の下では、関係者は合理的に行動した」**。失敗を生んだのは個人ではなく、**それを許した仕組み・条件**。
- 目的は「犯人捜し」ではなく「**システムと運用をどう変えれば同じ失敗を防げるか**」。
- （出典: Google SRE Book「Postmortem Culture」。ブレームレスであるほど正直な報告が集まり、再発防止に効く。）

### 5.2 いつポストモーテムを書くか（トリガー基準）
- ユーザ影響が一定以上／SLO違反／データ損失／対応が長時間化／再発／関係者が「書くべき」と判断、など**基準を事前に定義**。基準を満たしたら**必ず書く**（気分で決めない）。

### 5.3 ポストモーテムの構成要素
```text
1. 概要(Summary)      : 何が・いつ・どれだけの影響（1段落）
2. 影響(Impact)       : 対象ユーザ/機能、期間、SLO/売上/信頼への影響を定量化
3. タイムライン        : 検知→対応→復旧の時刻付き経緯（事実のみ）
4. 根本原因/寄与要因   : なぜ起きたか（単一犯人ではなく複数の要因）
5. 検知・対応の評価    : 早く気づけたか／対応は適切だったか／何が助けたか(Safety-II)
6. 再発防止アクション   : 具体策・オーナー・期限・追跡（最重要）
7. 教訓(Lessons)      : うまくいった点／いかなかった点／幸運だった点
```

### 5.4 根本原因分析 — 「1つの真犯人」を探さない
- **5 Whys** は入口として有用だが、**単線的に1つの原因へ収束させる罠**がある。複雑系の障害は通常**複数の寄与要因(contributing factors)の重なり**で起きる。
- **スイスチーズモデル**: 各防御層に空いた穴（欠陥）が偶然一直線に並んだとき事故が貫通する。→ 「どの層の穴を塞ぐか」を複数考える。
- 問いの立て方: 「誰がミスしたか」ではなく「**なぜその行動が"その時"は妥当に見えたのか／なぜ仕組みがそれを止められなかったのか**」。

```text
スイスチーズモデル（防御の多層化）
[コードレビュー] [自動テスト] [段階リリース] [監視/アラート] [Runbook]
     ○穴            ○穴          ○穴            ○穴          ○穴
      \             |            /              |            /
       ＼＿＿＿ 穴が一直線に並ぶと障害が貫通 ＿＿＿／
対策 = どれか1層でも穴を塞げば貫通を防げる → 複数層を同時に手当て
```

### 5.5 アクションアイテムの管理（ここで差がつく）
- ポストモーテムの価値は**アクションが実行されて初めて**生まれる。書いて終わりは最悪のアンチパターン。
- 各アクションは **SMART**（具体的/測定可能/割当済み/現実的/期限付き）に。**オーナーと期限を必須**とし、通常のバックログで**追跡・完了確認**する。
- 種類: 予防（再発の芽を断つ）／検知改善（次は早く気づく）／緩和（起きても影響を小さく）／対応改善（次は早く直す）。

### 5.6 学びを組織資産に
- ポストモーテムを**共有・公開**（社内）し、横展開。
- 蓄積したポストモーテムを**トレンド分析**（頻出原因・弱い依存・繰り返す穴）し、投資判断に使う。

### 5.7 そのまま使えるポストモーテム雛形

```text
# ポストモーテム: <インシデント名> (<日付>)

## メタ
- 重大度: SEV-<n>   状態: <ドラフト/レビュー済/完了>
- 起票者/レビュア: <名前>
- 関連: <インシデントチケット/アラート/PR>

## 1. 概要
<1〜3文: 何が起き、いつ、どれだけの影響があったか>

## 2. 影響
- 対象: <ユーザ/機能>   期間: <開始〜復旧>（合計 <分>）
- 定量: <エラー率/件数/SLO消費/売上/問い合わせ 等>

## 3. タイムライン（すべて UTC/JST 明記・事実のみ）
- HH:MM 変更/事象 …
- HH:MM 検知（誰が/何で）…
- HH:MM 一次対応 …
- HH:MM 復旧 …

## 4. 根本原因・寄与要因
- 直接の引き金: …
- 寄与要因(複数): …（設計/監視の穴/手順/負荷/依存 など）

## 5. 検知と対応の評価
- うまくいった点(Safety-II): …
- うまくいかなかった点: …
- 幸運だった点（次は無いかも）: …

## 6. 再発防止アクション
```

## 6. レジリエンス成熟度（自己診断の観点）

```text
Lv1 反応的   : 障害が起きてから場当たり対応。監視は最小限。属人的。
Lv2 管理的   : 監視/アラート・Runbook整備。SLO定義。ポストモーテム開始。
Lv3 予防的   : 設計パターン標準化。エラーバジェット運用。定期DR訓練。
Lv4 適応的   : カオスエンジニアリング常設。ブレームレスが文化。学習が投資に還元。
```
現在地を各局面（設計/監視/対応/学習）で評価し、1つ上の段へ具体アクションを積む。

## 7. アンチパターン（避けるべき）

- **無限リトライ／ジッター無し**: リトライストームで依存先を殺す。
- **タイムアウト未設定**: 障害が滞留・伝播し全体を巻き込む。
- **監視はあるがアラートが鳴りっぱなし（アラート疲れ）**: 本当の異常が埋もれる。
- **SLOが無い／100%を目指す**: 判断基準が無く、過剰投資か過小投資に振れる。
- **ポストモーテムが犯人捜し**: 情報が隠れ、再発する。
- **アクションアイテムを追跡しない**: 学びが実装されず同じ障害を繰り返す。
- **DR/バックアップを"取るだけ"でリストア未検証**: いざ復旧できない。
- **カオスを本番でblast radius無制限に実施**: 実験が本物の事故になる。

## 8. まとめ / 導入ロードマップ

```text
最初の一歩（コスパの高い順の目安）
1. 全外部呼び出しにタイムアウト＋リトライ(指数+ジッター)＋上限
2. 主要ユーザ体験にSLIを定義し、SLO＋エラーバジェットを1つ回す
3. 4 Golden Signals を可観測に（メトリクス/ログ/トレース）
4. 重大障害に「必ず」ブレームレス・ポストモーテム＋アクション追跡
5. サーキットブレーカー/バルクヘッド/フォールバックを重要依存に導入
6. DRリストア訓練 → 慣れたらカオス/ゲームデーへ
```

> 一文で: **「壊れない」を目指すのではなく、「壊れても続く・早く直る・学んで強くなる」を設計と運用と文化に埋め込む。** それがレジリエンス。
