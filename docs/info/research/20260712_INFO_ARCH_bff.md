# BFF（Backend for Frontend）— Webアプリ／バックエンド開発の実践ガイド

> 作成日: 2026-07-12 / STATUS: INFO / TOPIC: ARCH
> 対象: Web アプリケーション開発／バックエンド開発の文脈における **BFF（Backend for Frontend）**
> 図は全てプレーンテキスト（Mermaid 非依存）。

---

## 0. ひとことで

> **BFF = クライアント（フロントエンド）ごとに専用のバックエンドを1枚挟む**設計パターン。
> 各フロントエンド（Web／iOS／Android など）に「その画面に最適化したAPI」を提供し、背後の複数サービスの呼び出し・集約・整形を肩代わりさせる。

SoundCloud での実践（Phil Calçado ら）と Sam Newman の紹介で広まった、マイクロサービス時代の定番パターン。

---

## 1. どんな課題を解決するか

**単一の汎用API（1つのAPIで全クライアントを賄う）** には次の問題が出やすい:

- **オーバーフェッチ / アンダーフェッチ**: モバイルは通信・電池が貴重で最小限のデータが欲しいが、Web はリッチに欲しい。1つのAPIだと過不足が出る。
- **チャティ（おしゃべり）な通信**: 1画面を描くのに複数マイクロサービスへ何度も往復 → モバイルで特に遅い。
- **クライアント都合がAPIに漏れる**: 汎用APIに画面特有の分岐・整形が溜まり、肥大化・密結合化する。
- **チームの所有権が曖昧**: フロントの要求変更のたびに共有APIチームが詰まる（ボトルネック）。

```text
【従来: 汎用API 1枚で全部を賄う】
 Web ─┐
 iOS ─┼─▶ [ 汎用API(全部入り) ] ─▶ 各マイクロサービス群
 And ─┘        ↑ 過不足・チャティ・肥大化・所有権が曖昧
```

---

## 2. BFF の基本形

**クライアント体験（フロント）ごとに 1つの BFF** を置き、そのフロント専用に最適化する。

```text
【BFF: フロントごとに専用バックエンド】
 Web ──▶ [ Web BFF ]  ─┐
 iOS ──▶ [ iOS BFF ]  ─┼─▶ [ 認証 ][ 注文 ][ 在庫 ][ ユーザ ] … 下流マイクロサービス
 And ──▶ [Android BFF]─┘
             │
             └ 各BFFがやること: 複数サービスの呼び出しを集約 / 画面に最適な形へ整形 /
               不要データの除去 / 認証・セッション処理 / プロトコル変換
```

- 各 BFF は**その画面が必要とするデータだけ**を、**1回の呼び出しで返せる形**にまとめる。
- 下流サービスの変更（分割・URL変更等）を BFF が吸収し、**フロントを守る緩衝材**になる。

---

## 3. パターンの種類

- **クライアントタイプ別 BFF**: Web／iOS／Android など「体験の種類」ごとに1つ（最も一般的）。
- **チーム別（体験別）BFF**: 同じ Web でも「購入導線チーム」「管理画面チーム」で分ける等、**組織の所有権**に合わせる。Sam Newman は「1つの BFF は1つのユーザー体験に対応」を推奨。
- **GraphQL を BFF として使う**: クライアントが必要なフィールドを問い合わせできる GraphQL は BFF の役割（集約・整形・過不足解消）と相性が良く、BFF 実装の一形態になる。

---

## 4. API Gateway との違い（混同注意）

| 観点 | API Gateway | BFF |
|---|---|---|
| 目的 | 全クライアント共通の**横断的関心事** | **特定フロント専用**の集約・整形 |
| 主な責務 | ルーティング、認証、レート制限、TLS終端、監視 | 複数サービスの集約、画面向けデータ整形、プロトコル変換 |
| 数 | 通常1つ（全体の入口） | フロント／体験ごとに複数 |
| 誰が持つか | プラットフォーム/基盤チーム | 各フロントチーム |

```text
 クライアント ─▶ [ API Gateway (共通の横断処理) ] ─▶ [ 各BFF ] ─▶ マイクロサービス
                    認証/レート制限/監視            画面別の集約・整形
```
→ **両立する**。Gateway は「共通の門番」、BFF は「フロント専用の翻訳・集約係」。役割が違う。

---

## 5. メリット

- **フロント最適化**: 画面に必要なデータだけを1発で返せる → 通信回数・ペイロード削減、UX/性能向上。
- **疎結合**: 下流サービスの変更をBFFが吸収し、フロントへの影響を局所化。
- **所有権の明確化**: フロントチームが自分のBFFを持ち、共有APIのボトルネックを解消 → デプロイ独立性。
- **セキュリティ境界**: 認証・トークン取り扱い・機密フィルタをBFFに集約でき、フロントに秘匿情報を晒さない。

---

## 6. 注意点・アンチパターン

- **BFFの増殖と重複**: フロントごとに作ると共通ロジックが各BFFに重複しがち。共通部分は下流サービス／共有ライブラリへ寄せる。
- **BFFにドメインロジックを持たせない**: BFFの責務は**集約・整形・提示（プレゼンテーション）**。業務ルール（ドメインロジック）はBFFではなく下流サービスに置く。ここが漏れると「太ったBFF」＝新たなモノリスになる。
- **レイヤー追加によるレイテンシ／運用コスト**: 1ホップ増える。BFFの数だけ監視・デプロイ・障害点が増える。
- **N+1 BFF問題**: フロントの粒度に対してBFFを細かく作りすぎると管理不能に。「1体験1BFF」を目安に。
- **フロントとBFFの結合を活かす**: BFFは対応フロントと**同じチーム・近いリリースサイクル**で持つと真価が出る。

---

## 7. 実装の勘所

- **薄く保つ**: BFF = 「呼び出し集約 + 整形 + 認証」に徹する。ビジネス判断は下流へ委譲。
- **並列呼び出し + タイムアウト + フォールバック**: 複数下流を叩くので、並列化・タイムアウト・部分縮退（1サービス遅延で全滅させない）をBFFに実装（→レジリエンス設計）。
- **契約（スキーマ）をフロントと共同管理**: OpenAPI/GraphQLスキーマでフロント⇄BFFの型を固定。
- **キャッシュ**: 画面単位の集約結果をBFFでキャッシュし、下流負荷と応答を改善。

---

## 8. 使うべきとき / 避けるべきとき

**向いている:**
- クライアントの種類が複数（Web/モバイル/公開API等）で要求が大きく異なる。
- 多数のマイクロサービスを1画面で集約する必要がある。
- フロントチームがバックエンドの一部を自律的に持ちたい。

**過剰なとき:**
- クライアントが実質1種類で要求が単純 → 汎用API1枚で十分。BFFはただの中継層になり損。
- サービスが少なく集約の必要が薄い。

---

## まとめ

> BFF は「**フロントごとに専用の"翻訳・集約"バックエンドを1枚挟む**」パターン。過不足のないAPI・通信削減・疎結合・所有権の明確化が得られる一方、**薄く保つ（ドメインロジックを持たせない）／増やしすぎない**のが成功の鍵。API Gateway（共通の門番）とは役割が違い、両立する。
